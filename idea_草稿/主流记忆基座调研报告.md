# 主流记忆基座调研报告

日期：2026-07-25  
当前结论版本：论文与官方代码审计后的最终待审核版。主实验仍采用“一个可控 Single-Agent + 一个经典工程基座 + 一个强系统基座”的三层结构，但最终组合改为：

> **Unified Single-Agent Memory + LangMem-Agentic（official hot-path tool mode）+ MIRIX。**

MiM 的研究目标是**联合优化 memory construction 与 memory access**。三个基座都必须在两侧保留可被 Skill 影响的 Agent 决策；静态 ingestion 或固定 Top-k 本身不能被包装成 Construction/Access Agent。

## 当前三基座方案

当前建议组合为：

| 实验角色 | 推荐基座 | 年份/状态 | 主要价值 | MiM 插入点 | 当前判断 |
| --- | --- | --- | --- | --- | --- |
| 机制可控的内部基座 | Unified Single-Agent Memory | 本项目定义 | 同一 LLM Agent 在构建与访问阶段分别操作工具；最适合故障归因、模块消融和验证 Skill Bank 机制 | Construction Skill Bank + Access Skill Bank | **确定保留**；controlled baseline，不冒充有外部影响力的独立系统 |
| 经典工程基座 | LangMem-Agentic | 2025 SDK；MIT；约 1.5k stars | LangChain/LangGraph 官方生态；同一 ReAct agent 在 hot path 自主调用 `manage_memory` 与 `search_memory` | 外层 agent 的 Construction/Access policy prompt 与运行轨迹 | **确定保留**；工程经典而非学术经典，必须固定为 official hot-path tool mode |
| 当前强系统基座 | MIRIX | 2025 arXiv；Apache-2.0；约 3.5k stars | 六类记忆、Meta/Memory Managers 与 Chat Agent，双侧操作空间最完整 | Memory Managers + Chat Agent/Active Retrieval | **确定保留**；承担复杂架构与强外部有效性验证 |

三者分别回答不同问题：

1. `Unified Single-Agent + MiM`：MiM 的双 Skill Bank、故障归因和回放验证是否真正有效。
2. `LangMem-Agentic + MiM`：MiM 是否能增强一个有工业影响力、低改造成本的官方 agent memory SDK，而不是只在自建基座上有效。
3. `MIRIX + MiM`：MiM 是否能增强一个已有完整 construction/access 组织的复杂多智能体 LTM。

## 筛选原则与实验角色

MiM 的研究定位不是 access-only，也不是给静态检索器简单增加一个 ReAct 外壳，而是：

> 从下游失败中区分 Construction Failure、Access Failure 与 Other，分别学习可检索、可演化、可回放验证的 Construction Skill 和 Access Skill，从而联合改善已有记忆系统未来的构建与访问决策。

主实验不再要求三个基座全部都是知名外部系统。一个自建 controlled baseline 可以换取清楚的机制验证，另外两个外部基座负责影响力、代表性和强度。具体门槛如下：

1. **Unified Single-Agent**：构建和访问都必须由同一个 Agent 在不同阶段自主决策，且 `base` 与 `base + MiM` 使用完全相同的工具、轮数和预算。
2. **经典工程基座**：应有明确的 construction/access 工具边界、跨会话持久记忆、足够社区影响力和较低适配成本；不强求正式论文。
3. **当前强基线**：construction 与 access 两侧都应有 Agent policy；仅有强 Retrieval Agent 仍不足以进入三组联合优化主表。
4. 只有 embedding Top-k、固定多路召回或固定 reranker 的系统，不得描述成原生 Access Agent；它们可以进入“MiM 补全 access”的辅助实验。

2026 survey [2603.07670](</D:/Documents/Project/Memory_in_Memory/reference/memory_bases_2026/2603.07670_memory_survey_autonomous_llm_agents.pdf>) 把 agent memory 形式化为 write--manage--read loop。这个视角支持我们把 MiM 作为局部增强插件：它可以插 write，也可以插 read，也可以插 manage。

外部候选继续采用四个优先级：

1. 是否足够知名/主流：论文 venue、arXiv 可见度、GitHub stars、是否被其他 benchmark/survey 比较。
2. 是否容易插入：代码、license、API、模块边界、是否已有本地 baseline。
3. 是否有预期提升空间：不能过度 prompt-heavy 到 MiM 很难贡献，也不能完全工程黑盒。
4. 是否支持论文叙事：主基座覆盖 controlled/industrial/multi-agent 三种角色；2026 新工作通过 MemSkill、MemMA、PlugMem、MemMachine/MRAgent 压力测试进入直接比较，不为“年份新”牺牲双侧门槛。

实现难度统一按以下条件估计：一名熟悉 Python/LLM agent 的工程人员、MiM 的归因器与双 Skill Bank 核心已可复用、只计算“基座接入 + 小规模跑通 + 轨迹记录”，不含全量 API 评测时间。难度不是按论文图复杂度主观判断，而是依据官方代码中的 prompt/tool 注入点、可观测轨迹、评测脚本与基础设施依赖。

## MemMA 的真实实验逻辑及其与 MiM 的边界

资料来源：

- [MemMA 论文（arXiv HTML）](https://arxiv.org/html/2603.18718v1)
- [MemMA 官方仓库](https://github.com/ventr1c/memma)

MemMA 选择的 Single-Agent、A-MEM 和 LightMem 更准确地说是三个 **storage backend**，而不是三个原生具有 Construction Agent 与 Access Agent 的完整基座。它把后端统一抽象为记忆写入/更新和 `search(query, top-k)`，然后在外部增加 Meta-Thinker、Memory Manager、Query Reasoner 与 Answer Agent。

其访问流程是：

```text
初始问题
→ 固定 backend.search()
→ Meta-Thinker 判断证据是否充分并诊断 evidence gap
→ Query Reasoner 生成正交查询
→ 再次调用同一固定 retriever
→ 合并证据并继续或停止
```

因此，MemMA 不是在优化三个系统原有的 Access Agent，而是在 backend 外部创建一个较小的访问操作空间：`ANSWERABLE/NOT_ANSWERABLE`、缺口诊断、下一条查询和停止。它没有证明自己能增强已经成熟的多工具 Access Agent，也没有覆盖 memory-type routing、retrieval-tool selection、graph traversal、动态预算和 branch pruning 等更丰富策略。

从实验设计看，选择这些后端是有意为之：三者都容易统一成 `write/update/search` 接口，可以避免 MemMA Query Reasoner 与原生 Access Agent 争夺控制权，同时从 one-shot retrieval 升级为多轮查询也具有较大提升空间。因此，它的三后端实验首先服务于 **storage-backend portability**，而不是已有 Agent policy 的跨基座优化。

MemMA 所称的 joint coordination 是：

1. Meta-Thinker 在构建时为 Memory Manager 提供保留、合并和冲突处理指导。
2. Meta-Thinker 在访问时为 Query Reasoner 提供 evidence-gap diagnosis。
3. Session 后生成 synthetic probe QA，用失败 probe 产生 repair fact。
4. 将 repair fact 以 `SKIP/MERGE/INSERT` 方式直接修补事实 Memory DB。

这与 MiM 的区别是：

| 维度 | MemMA | MiM |
| --- | --- | --- |
| 被优化对象 | storage backend 外部的统一 controller | 已有 Construction/Access Agent 的策略 |
| 访问增强 | 当前问题上的 gap diagnosis + query rewrite | 从历史失败中检索可复用 Access Skill |
| 失败处理 | 生成 repair fact，直接修补事实记忆 | 归因 Construction/Access/Other，学习程序性 Skill |
| 长期积累对象 | 用户事实和修复后的 Memory DB | “以后应如何构建/访问”的双 Skill Bank |
| 验证 | probe QA 检查当前 memory | Candidate Skill 强制验证、自然验证与回归检查 |

所以 MemMA 的跨 backend 实验能够证明 controller 对不同存储实现具有可移植性，但不能充分证明它能优化已有 agent policy。MiM 主实验采用“controlled Single-Agent + 经典工程 Agent SDK + 强多智能体系统”，正是为了避免把“增加 Agent loop”的收益误认为“Skill Bank 学习”的收益。

## MemSkill：最接近 Construction Skill Bank 的直接竞争者

资料来源：

- [MemSkill 论文](https://arxiv.org/abs/2602.02474)
- [MemSkill 官方仓库](https://github.com/ViktorAxelsen/MemSkill)

MemSkill 将记忆构建操作改写为可学习、可演化的 skills：Controller 从 Skill Bank 选择少量相关技能，Executor 按技能生成记忆，Designer 从困难样例中新增或改写技能。它在 LoCoMo、LongMemEval、HotpotQA 与 ALFWorld 上评测，官方仓库约 487 stars、Apache-2.0。

它与 MiM 的 Construction Skill Bank 高度相邻，但不是合适的“被插基座”：

- MemSkill 的技能主要服务于 extraction/consolidation/pruning，即 construction；它没有学习一个多工具、可多轮停止的 Access Agent policy。
- Controller 的技能选择需要 PPO/训练流程，且 Executor、Designer 与其 Skill Bank 共同构成方法本体。去掉 PPO 后只剩“语义 Top-k 选 instruction + LLM extraction”，会失去论文主要特色。
- 把 MiM 插入 MemSkill 会造成 skill bank 套 skill bank，和 `PlugMem + MiM` 一样难以归因。

因此 MemSkill 应作为**construction-side 最近邻 competitor**，比较：

```text
Base Construction Agent
Base + MemSkill
Base + MiM-Construction
Base + MiM-Joint
```

底层 Memory DB、模型和构建样本保持一致；重点比较 MemSkill 的 PPO selector + Designer 与 MiM 的 failure attribution + replay validation。若完整复现官方训练，预计 **7–12 个工程日**并需要训练算力；不建议为主实验把它改造成双侧插件。

## 1. Unified Single-Agent Memory：机制可控基座

本基座由项目实现，不作为外部知名系统，而作为 controlled baseline。其关键要求是：**同一个 LLM Agent 在两个阶段工作，但阶段工具和 Skill Bank 分离。**

建议最小操作空间：

```text
Construction:
SEARCH_EXISTING / ADD / UPDATE / DELETE / NOOP / COMMIT

Access:
SEMANTIC_SEARCH / KEYWORD_SEARCH / TEMPORAL_SEARCH / METADATA_FILTER / GET_BY_ID / STOP_AND_ANSWER
```

具体工具可以继续精简，但必须保留以下自主决策：

- 构建侧：写什么、更新什么、是否删除/合并以及何时提交。
- 访问侧：搜什么、是否改写查询、是否继续检索以及何时停止回答。

公平性约束：

- `Single-Agent` 与 `Single-Agent + MiM` 使用相同模型、Memory DB、工具集合、最大轮数、token/tool-call budget 和 answer prompt。
- MiM 只能增加 Construction/Access Skill 的检索、注入、学习和验证，不能额外增加工具或访问轮数。
- 虽然底层执行者是同一个 Agent，Construction Skill Bank 与 Access Skill Bank 仍须分开，以检验两类程序性经验是否具有不同适用边界。

定位：主实验的机制验证与消融锚点；不承担外部影响力论证。

## 2. LangMem-Agentic：经典工程基座

资料与代码：

- [LangMem 官方文档快照](</D:/Documents/Project/Memory_in_Memory/reference/memory_bases_2026/langmem_official_docs.html>)
- [LangMem memory tools API 快照](</D:/Documents/Project/Memory_in_Memory/reference/memory_bases_2026/langmem_memory_tools_api.html>)
- [LangMem GitHub 快照](</D:/Documents/Project/Memory_in_Memory/reference/memory_bases_2026/langmem_github_snapshot.html>)
- [本地官方仓库](</D:/Documents/Project/Memory_in_Memory/baseline/langmem>)
- [官方 GitHub](https://github.com/langchain-ai/langmem)

本次源码审计锁定本地 commit `a2d580946465137c89162e67dc0b18108bd4850c`。

### 它到底是不是经典基座

LangMem 不是“高引用的学术经典”，因为它没有对应的正式研究论文；但它可以作为**经典工程基座**：

- 它来自 LangChain/LangGraph 官方生态，MIT 许可，约 1.5k stars，接口稳定、社区可见度足够。
- MIRIX、LightMem、MRAgent、MemMA、Mnemis、MemMachine 等后续论文都将 LangMem 当作 baseline 或工程参照。跨论文数值不一致，反而说明必须精确定义运行模式。
- 它比 MemGPT/Letta 新，避免“经典但过旧”；又比许多 2026 单篇论文仓库成熟，符合“容易跑出结果、少做额外 prompt engineering”的要求。

因此，稿件中应写成：

> `LangMem-Agentic (official hot-path tool mode)`

不能只写 `LangMem`。很多论文复现的是后台 extraction/summary + similarity Top-k 的被动配置，那不等于官方 hot-path agentic 配置。

### Construction 和 Access 是否 agentic

官方源码给出了两个可直接挂到同一 ReAct agent 的工具：

1. `create_manage_memory_tool(...)` 暴露 `create/update/delete`。Agent 自主决定何时写、写什么、更新或删除哪条记忆，也可以不调用。
2. `create_search_memory_tool(...)` 暴露 `query/limit/offset/filter`。Agent 自主决定是否搜索、何时搜索、查询内容、过滤条件、是否再次搜索以及何时停止回答。

所以 LangMem hot-path 在 orchestration 层是双侧 agentic。其边界也必须说清：底层 `BaseStore.search()` 仍是 semantic/exact primitive，官方只抽象为一个 `search_memory` 工具；它没有 MIRIX 那样的 memory-type routing 或 MRAgent 那样的图遍历工具空间。

### 与自建 Single-Agent 是否重复

二者结构相近，都是单 Agent + memory tools；如果都实现成“CRUD + 一个向量搜索”，主实验确实重复。保留二者的前提是严格区分实验角色和工具面：

| 维度 | Unified Single-Agent | LangMem-Agentic |
| --- | --- | --- |
| 角色 | 内部 controlled baseline | 外部工业/生态 baseline |
| 存储 | 最小 JSON/SQLite 平面表 | 官方 LangGraph `BaseStore`、namespace、schema |
| Construction | 显式 `SEARCH_EXISTING/ADD/UPDATE/DELETE/NOOP/COMMIT` | 原生 `manage_memory` |
| Access | 显式多元工具：semantic、keyword、temporal、metadata、get-by-id、stop | 原生单一 `search_memory(query, limit, offset, filter)` |
| 允许的额外能力 | 不加 namespace、后台抽取、prompt optimizer | 保留官方工具；不人为补多路工具 |
| 论文作用 | 机制上限、归因与消融 | 证明 MiM 对现成 SDK 也有效 |

这不是两个“异构架构”的证据，而是**内部可控验证 + 外部工程复现验证**。真正的架构多样性由 MIRIX 提供。

### 论文中如何报告表现

不同论文的 LangMem 数值不能直接横比，因为模型、judge、memory construction 与 access mode 不同：

| 来源 | 数据集/配置 | 报告值 | 解释 |
| --- | --- | ---: | --- |
| LightMem | LoCoMo，GPT 系 | 57.20 | 更接近被动 LangMem baseline |
| LightMem | LongMemEval，GPT 系 | 37.20 | 同上 |
| MIRIX | LoCoMo，GPT-4o-mini / GPT-4.1-mini | 58.10 / 78.05 | backbone 影响很大 |
| MRAgent | LoCoMo，Gemini / Claude | 62.86 / 78.61 | 不能外推到 GPT-4o-mini |
| MemMA | LoCoMo，GPT / Claude | 30.26 / 44.74 | backend/controller 配置不同 |

这些结果说明 LangMem 有明显提升空间，但不能证明 official hot-path 一定弱。主实验必须在同一模型、同一 split、同一预算下重跑 `LangMem-Agentic` 与 `LangMem-Agentic + MiM`。

### MiM 接入方案与真实工作量

无需 fork 或改写 LangMem 内部源码：

- Construction Skill 在每次调用前检索，注入外层 ReAct agent 的 construction policy/context；底层仍调用官方 `manage_memory`。
- Access Skill 注入同一 Agent 的 retrieval policy/context；底层仍调用官方 `search_memory`。
- 从 LangGraph message/tool-call 轨迹记录查询、参数、工具结果、停止与答案；从 `BaseStore` 导出前后快照供 Construction/Access Failure 归因。
- 自建 LoCoMo/LongMemEval runner，因为官方 LangMem 仓库没有这两个 benchmark 的开箱即用脚本。

在 MiM 公共核心已存在的前提下，预计 **5–8 个工程日**：1–2 日复现 hot-path 与持久化，2–3 日完成双侧 adapter/trace，2–3 日完成 benchmark runner 与小规模校验。主要风险不是改库，而是保证数据按 conversation 隔离、轨迹与 memory snapshot 可重放。

LangMem 还原生提供 `create_prompt_optimizer`。它会从 trajectory/feedback 全局改写 prompt，与 MiM 的“从失败中学习程序性经验”存在近邻重叠。基础组必须关闭它，并增加：

```text
LangMem-Agentic
LangMem-Agentic + Native Prompt Optimizer
LangMem-Agentic + Global Reflection
LangMem-Agentic + MiM-Construction
LangMem-Agentic + MiM-Access
LangMem-Agentic + MiM-Joint
```

定位：三主基座中的经典工程锚点；接入成本低、预期较容易观察增益，但不承担学术 venue 论证。

## 3. MIRIX：强多智能体 LTM 架构

资料已存：

- [2507.07957_mirix.pdf](</D:/Documents/Project/Memory_in_Memory/reference/memory_bases_2026/2507.07957_mirix.pdf>)
- [2507.07957_mirix.txt](</D:/Documents/Project/Memory_in_Memory/reference/memory_bases_2026/2507.07957_mirix.txt>)
- [mirix_github_snapshot.html](</D:/Documents/Project/Memory_in_Memory/reference/memory_bases_2026/mirix_github_snapshot.html>)
- [mirix_github_api.json](</D:/Documents/Project/Memory_in_Memory/reference/memory_bases_2026/mirix_github_api.json>)

GitHub API 核验（2026-07-23）：`Mirix-AI/MIRIX` 3,558 stars、290 forks、Apache-2.0、Python，2026-07-15 仍有 push。

选择理由：

- 它是完整的跨会话 LTM system，包含 Core、Episodic、Semantic、Procedural、Resource 和 Knowledge Vault 六类记忆，而不是单独的检索算法。
- 架构具有“较经典”辨识度：沿用认知科学中的 episodic/semantic/procedural 分型，同时加入 Core、Resource、Vault 以覆盖现代 agent 的画像、文档和敏感信息。
- 时间位置合适：2025 年工作、约 3.6k stars，已经形成一定社区认知，又没有老到像 2023 MemGPT。
- 构建端由 Meta Memory Manager 将输入路由给六个专职 Memory Managers，并协调更新、去重和结构化写入。
- 读取端确有 Access Agent。Chat Agent 先对六类记忆做 coarse search，再分析问题、判断哪些 memory components 需要 targeted search，并自主选择 `embedding_match`、`bm25_match`、`string_match` 等方法。
- 论文还定义 Active Retrieval：agent 先生成当前 topic，再自动触发记忆搜索，避免依赖用户显式要求“search memory”。

可插入方式：

- MiM-Construction：增强 Meta Memory Manager 的 memory-type routing，以及六个 Memory Managers 的写入、去重、压缩和更新策略。
- MiM-Access：替换或增强 Chat Agent 的 topic/query generation、memory-component selection、retrieval-method selection、targeted re-search 和停止条件。
- 为保持 baseline 身份，应保留 MIRIX 的六类 memory schema，只修改控制策略，不改成 MiM 自己的一套存储结构。

风险：

- 当前主分支已演进为独立 memory API；代码审计确认 Chat/Memory Agents 与 eval 路径仍在，但必须锁定评测分支/commit。仅调用新版 `search` API 不满足实验要求。
- 论文目前主要是 arXiv，正式 venue 权威性弱于 Hindsight；其优势来自完整架构、3.6k 社区影响力和真正的多智能体 access control。

### 官方代码审计与真实工作量

官方当前 `main` 已转向“pure memory system API”，但并未删除多 Agent 内核：代码仍包含 Chat Agent、Meta Memory Agent、六类 Memory Agent、各自 system prompts 与 memory tools；仓库还保留 `evals/main_eval.py`、`evals/mirix_memory_system.py` 和 LoCoMo 配置。远端同时保留 `desktop-agent`、`public_evaluation`、`locomo-eval` 等分支。本次审计锁定 `main` commit `51f3342d5366b0e215439581f92e0323227146af` 与 `locomo-eval` commit `69393ec8fb8932d1bc3415a51fa4383710b0d74e`。

这意味着 MIRIX **可做，但不能只调用新版统一 search API**。建议锁定同一 commit 的 LoCoMo/evals 路径：

- Construction Skill 分别注入 Meta Memory Manager 与各专职 Memory Manager 的 system context，保留原有 insert/merge/update/finish tools。
- Access Skill 注入 Chat Agent，保留 `search_in_memory`、时间范围检索、component/method selection 与原始停止机制。
- 在 `Agent.step()`/tool-call trace 外围收集两侧轨迹，不修改六类 memory schema。
- 使用官方 eval runner 负责 LoCoMo ingestion/answer，再接 MiM 的 failure attribution 与 replay。

基础设施比 LangMem 重：官方快速开始需要 Docker 后端，搜索依赖 PostgreSQL-native BM25/可选向量检索；论文版、当前 API 与 eval 分支存在版本漂移。预计 **10–15 个工程日**：2–3 日锁版本和跑通原始 LoCoMo，4–6 日接 construction/access adapters 与轨迹，2–3 日做快照/回放，2–3 日处理并发、数据库重置和公平性校验。建议先用 1 个 conversation 做 2–3 日 go/no-go pilot。

MIRIX 的专职 Agent prompts 很长、原生控制策略也强，MiM 的边际增益预计小于 Single-Agent/LangMem；但这正是“强基线仍可提升”的关键证据。不得为追求增益而删减 MIRIX 原 prompt 或额外提高 `+MiM` 预算。

定位：三主基座中的强系统锚点；它同时提供双侧 Agent policy 和与前两个单 Agent 基座不同的多智能体/多记忆架构。

机制审计结论：

- 权威性来自“正式 ACL 出版 + 18.7k stars + 完整开源系统”的交集，知名度量级明显高于刚发布、仅几十到几百 stars 的新方法。
- 它提供 `retain`、`recall`、`reflect` 三个清楚的 memory operation，并将事实、经历、观察和观点分成四类网络。
- 写入端由 LLM 抽取 narrative facts、识别实体并维护 temporal/entity links，存在智能构建过程。
- Access 模块 TEMPR `recall` 固定执行 vector、BM25、graph、temporal 四路检索，再经 RRF 和 cross-encoder 排序。
- CARA `reflect` 即使会调用 `recall`、`expand` 等工具，仍属于回答/反思层；它没有接管 TEMPR 的查询规划、通道路由、图扩展深度和检索预算。

可作为辅助工作的方式：

- MiM-Access：接在 `reflect -> recall/expand` 之间，控制 query rewriting、检索通道选择、graph expansion depth、token budget 和停止条件。
- MiM-Construction：接在 `retain` 的事实抽取、实体消歧、link construction 和 observation 更新处。
- 最稳妥的实验是保留 Hindsight storage 与四网络结构，只替换/增强 agent 的访问策略，避免把系统整体重写后失去 baseline 身份。

定位：高知名度相关系统，或 `Hindsight + MiM-Access` 辅助实验；不进入当前两个外部主基座。

- Access-only adapter 很容易：修改/包装三个 agent prompt 并记录子查询即可，预计 **4–7 个工程日**。

定位：不进入三组 `A<A+X` 联合优化主表；作为 `MemMachine + MiM-Access` 强访问压力测试或 upper baseline。

资料已存：

代码核验（2026-07-23）：`Ji-shuo/MRAgent` 约 222 stars、21 forks、Python；官方仓库包含 LoCoMo/LongMemEval 数据入口、图记忆构建、七类访问工具、多轮 tool-calling loop 与评测脚本。当前仓库只有 1 个 commit，未提供 `LICENSE`。

选择理由：

- 学术身份强：论文被 ICML 2026 接收，且由 ICML 官方 2026 paper list 收录；相较仅有 arXiv 的新系统，更能支撑主实验的学术叙事。
- 它是完整 LTM pipeline，不只是一个检索算子。构建端把对话蒸馏为 Cue–Tag–Content 异构图，包含 episodic、semantic、topic/personal 等内容；读取端再在该持久图上主动重构。
- 它有严格意义上的 Access Agent。agent 根据 query、当前 active set 和已积累证据，自主选择正向/反向遍历动作，生成新线索，裁剪无关分支，并判断继续检索或提前回答。
- 开源实现将这种机制落为七类工具：`edges_by_tag`、时间、事件关键词、事件上下文、人物信息、人物属性和主题事件查询；LLM 看到工具结果后可继续调用，默认最多 8 轮。
- 原生支持 LoCoMo 与 LongMemEval，实验适配成本明显低于 AgeMem；论文也直接以 A-Mem、MemoryOS、LangMem、Mem0 和 RAG 为基线。
- 论文在 LoCoMo 上用 Gemini-2.5-Flash 与 Claude-Sonnet-4.5 报告结果，并用 GPT-4o-mini 作 judge。它适合作为 2026 前沿强基座，但不能把论文的性能数值直接当作 GPT-4o-mini access-agent 的预期结果。

可插入方式：

- 保留 MRAgent 的 Cue–Tag–Content 图、七类底层工具和统一检索预算；否则会失去 `MRAgent + MiM` 的基座身份。
- MiM-Access 只增强 agent policy：根据失败轨迹提供可积累 skill，影响 tool selection、参数/线索生成、forward/reverse traversal、branch pruning 与 stop/answer 判断。
- 适配器放在 MiM 工程侧，通过 prompt/tool-policy injection 接入，不直接改写或再发布 MRAgent 源码。
- 主表至少报告 `MRAgent`、`MRAgent + MiM`，并固定相同底层图、工具集合、最大轮数、工具调用预算和回答模型。

风险：

- 这是最接近 MiM access-side 贡献的基座之一，增益可能小于在较弱 access agent 上的提升；但若仍有提升，论证力度也最大。
- 仓库仅 1 个 commit、无 release、无明确 license，工程成熟度不如 MIRIX/MemMachine。学术实验可调用公开代码，但修改版再分发前应向作者确认许可。
- 论文的强结果依赖 Gemini/Claude access backbone；项目已计划采用 GPT-4o-mini，必须先做小规模 tool-use pilot。若 GPT-4o-mini 无法稳定选择图工具，应报告模型能力限制，不能靠改变预算或额外强模型为单个基座兜底。

定位：不再默认占据第三主基座。保留为 2026 主会前沿、强 Access-Agent 压力测试候选；只有当 MemMachine 构建侧不合格且 MRAgent 的工程、license、模型依赖问题可控时，再重新进入审核。

## PlugMem：降为直接竞争方法，不再作为被插基座

PlugMem 的 LLM controller 的确符合 Access Agent：它会选择 memory type、生成下一跳计划、重写查询、聚焦候选并提前停止。因此，排除它不是因为机制不合格，而是因为实验角色不合适。

PlugMem 本身就是 task-agnostic plugin memory module。把 MiM 再插到 PlugMem 上会出现两个问题：

1. `PlugMem + MiM` 是插件套插件，读者难以判断提升来自 MiM 的 skill accumulation，还是来自替换/叠加 PlugMem controller。

### AgeMem-AgentScope：无 RL 会失去方法特色

资料已存：

- [2026.acl-long.981_agemem.pdf](</D:/Documents/Project/Memory_in_Memory/reference/memory_bases_2026/2026.acl-long.981_agemem.pdf>)
- [2026.acl-long.981_agemem.txt](</D:/Documents/Project/Memory_in_Memory/reference/memory_bases_2026/2026.acl-long.981_agemem.txt>)

AgeMem 是 ACL 2026 Long Paper，将 `Retrieve_memory`、`Add/Update/Delete_memory` 与 `Summary/Filter_context` 暴露为 AgentScope agent actions。读取时 agent 自主决定是否调用、查询内容、`top_k` 与 metadata filter，因此虽然底层 primitive 仍是 semantic top-k，它整体仍属于 Access Agent；这与 A-Mem 的固定 embedding + top-k 调用不同。

AgeMem 的核心贡献不是“AgentScope 提供了一组 memory tools”，而是通过 Trinity-RFT/GRPO 学到统一的 STM/LTM 管理策略。**去掉 RL 后，系统会退化为一个普通 AgentScope ReAct agent + memory tools，基本失去 AgeMem 的方法辨识度**；这样的 no-RL 版本只能叫 tool-agent ablation，不能当作 AgeMem 基线。

论文未在 LoCoMo 或 LongMemEval 上评测。完整迁移不只是写 adapter，还要重建 trajectory、reward、Trinity-RFT/GRPO 与 checkpoint 评估；仅 6 个训练 conversation 也难以支撑可靠 RL。预计完整复现与 LoCoMo 迁移需 **12–20 个工程日 + RL 训练资源**。故它适合作为跨任务扩展或 related work，不进入主表；不要用 no-RL 版本降低难度后仍沿用 AgeMem 名称。

| Mem0 | 约 61k stars，工程/社区最强 | 用户已明确排除；本地版本没有真正 Access Agent |

从“容易出效果”排序，预期是 `Unified Single-Agent > LangMem-Agentic > MIRIX`；从论证强度排序则相反。这个梯度是合理的：前两组负责稳定显著性和机制归因，MIRIX 负责证明 MiM 不是只对弱/自建 prompt 有效。

## 主实验与辅助实验安排

当前主实验方案：

1. `unified_single_agent_memory`
2. `langmem_agentic_hot_path`
3. `mirix_2025_multi_agent_ltm`

这三个基座分别对应 controlled、industrial 和 complex-system 三种证据。Single-Agent 与 LangMem 的架构相似性必须主动披露；二者的价值不是“多样性”，而是内部机制与外部 SDK 的双重验证。架构多样性由 MIRIX 提供。

LoCoMo 采用 6:2:2 的 conversation-level 划分，而不是把同一 conversation 的 QA 随机拆到不同集合：

- train 6 个 conversation：只用于 MiM skill 的生成、更新与学习。
- validation 2 个 conversation：选择 prompt/version、技能数量、检索预算与停止阈值。
- test 2 个 conversation：冻结 MiM skills、prompt、模型和所有超参数后一次性评测。
- 三个主基座、PlugMem 直接对比和所有辅助实验使用同一组 conversation IDs；原始基座若不需要训练，也必须只在 train/validation 上调参，避免 session/人物/事件泄漏。
- 每个主基座都同时报告 `base` 与 `base + MiM`。两者固定相同模型、底层 memory store、工具集合、最大访问轮数和 token/tool-call budget，唯一变量是 MiM skill layer。

Single-Agent 的核心消融：

1. `Single-Agent`
2. `Single-Agent + Global Reflection Prompt`
3. `Single-Agent + Retrieved Failure Cases`
4. `Single-Agent + MiM-Construction only`
5. `Single-Agent + MiM-Access only`
6. `Single-Agent + MiM-Joint`

其中第 4–6 项用于验证联合优化是否成立。除了最终 QA 指标，还应分别统计 construction failure、access failure 与 other failure 的数量变化。只有当 `MiM-Joint` 稳定优于两个 single-side 版本，并且两类记忆错误都下降时，才能支持“联合优化”而非简单模块叠加。

三个主基座都应至少报告：

```text
Base
Base + Global Reflection
Base + MiM-Construction
Base + MiM-Access
Base + MiM-Joint
```

LangMem 额外报告 `Base + Native Prompt Optimizer`。`Base + X` 与 `Base` 的模型、底层 store/schema、原生工具集合、最大轮数、token/tool-call budget 必须一致；MiM 不能通过新增工具或提高预算获得优势。

辅助实验/消融：

- `plugmem_direct_competitor`：与 MiM 做同预算的插件级横向比较，不做 `PlugMem + MiM`。
- `memskill_construction_competitor`：比较 PPO/Designer 式 construction skill evolution 与 MiM-Construction/MiM-Joint。
- `memmachine_plus_mim_access`：在官方强 Retrieval Agent 上测试 MiM 的边际 access 收益，不宣称联合优化。
- `mragent_plus_mim_access`：作为多工具图检索压力测试，固定图与七类工具。
- `hindsight_plus_mim_access`：验证 MiM 能否把高知名度固定检索 LTM 升级为 Access-Agent LTM。
- `memoryos_plus_mim_access`：验证 MiM 能否把经典分层 LTM 升级为 Access-Agent LTM，只作为辅助实验。
- `lightmem_plus_mim_access`：验证轻量静态检索 LTM 的 access-side 升级，只作为辅助实验。
- `a_mem_plus_mim_access`：验证 MiM 能否给 construction-agentic / access-static 系统补 access。
- `simplemem_plus_mim`：强 prompt-heavy upper baseline，检验 MiM 的边际收益边界。
- `memori_plus_mim_access`：验证 MiM 对 structured memory layer 的局部增强。

对于 LightMem、A-MEM、Hindsight、MemoryOS 等原生静态访问系统，必须加入 `backend + generic Access Agent` 控制组：

```text
Native Backend
Backend + Generic Access Agent
Backend + Generic Access Agent + Global Reflection
Backend + MiM
```

否则无法区分提升来自“新增 Agent loop”，还是来自 MiM 的失败归因和 Skill Bank 学习。

MemMA 的实验角色：

- 作为最近邻联合协调方法进行直接比较。
- 重点比较其“当前实例上的 Meta-Thinker + query refinement + fact repair”与 MiM 的“跨实例 failure attribution + 双 Skill Bank + replay validation”。
- 不把 `Single-Agent/A-MEM/LightMem + MemMA` 的提升解释为“优化了原生 Access Agent”，而解释为“MemMA controller 对 storage backend 的增强”。

## 当前一句话结论

> **Unified Single-Agent Memory + LangMem-Agentic + MIRIX。**

它形成：

> **机制可控基座 + 经典工程基座 + 强多智能体系统基座。**

Unified Single-Agent 用于证明双 Skill Bank、故障归因和回放验证本身有效；LangMem-Agentic 用于证明 MiM 能低改造成本增强有工业影响力的官方 SDK；MIRIX 用于证明 MiM 能增强已有复杂 construction/access 架构。

最终不选 MemMachine 不是因为它弱，而是 construction-side code audit 已确认其写入遵循 ground-truth-preserving 固定 ingestion，不能支撑双侧联合优化。MemMachine 与 MRAgent 作为强 Access 压力测试；LightMem、A-MEM 等静态访问系统作为补全 access 的辅助实验；MemSkill、PlugMem 与 MemMA 作为最近邻竞争方法。LangMem 与 Single-Agent 的重叠通过“官方单搜索工具 vs 自建多元检索工具、外部 SDK vs controlled baseline”显式控制，不把二者夸大为两个异构系统。
